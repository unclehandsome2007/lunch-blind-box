開發動機：為什麼需要
Lunch Blind Box

每天過著規律的生活，心裡常吶喊著「今天想吃點別的」、「但我懶得想」。我們分析了日常午餐決策的核心痛點：

  • cancel 選擇障礙： 每天面臨嚴重的午餐選擇困難，不想重複吃昨天吃過的餐廳。
  • map 距離誤差： 錯誤估計直線距離與實際步行的落差，導致超過休息時間才匆忙趕去上課。
  • call_split 聚餐摩擦： 和同學一起吃飯需考量不同地點出發的距離，飯後還要處理繁瑣的買單平分計算。

開發遭遇困難與解決方案

實作過程中克服的開源圖資與即時系統技術瓶頸。

1. OSRM 荒謬繞路防呆

困難： OSRM 導航引擎有時因缺乏巷弄標記，規劃出「繞大馬路一大圈才抵達」的超時路線。

解決： 實作「直線防呆演算法」，若 OSRM 步行距離超過直線距離 3 倍，系統會沒收導航線並改用 1.2 倍直線距離保底計算。

2. 底層經緯度格式衝突

困難： OSRM 回傳 GeoJSON 為 [經度, 緯度]，但 Folium/Leaflet 規定必須為 [緯度, 經度]，導致路線飄移。

解決： 撰寫 Python 串列推導式 (List Comprehension)，在注入 Folium 前瞬間反轉節點座標矩陣，解決套件間格式衝突。

3. 圖資黑名單過度攔截

困難： 為避免抽到政府機關封鎖了 building 等標籤，但許多小吃店因此被誤殺，導致「找不到結果」。

解決： 實作「動態權重過濾器」。當輸入明確食物關鍵字時自動放寬限制，無關鍵字隨機抽取則維持嚴格黑名單。

4. 多人狀態競賽 (Race Condition)

困難： 多人房間中同時按「抽獎」會導致伺服器崩潰，且條件設定若只存網址會無法同步給新朋友。

解決： 導入 Firebase「狀態鎖 (Locking) 機制」，全體強制鎖定並同步彈出黑屏動畫，並將設定全面雲端化收納於 Modal 中。
